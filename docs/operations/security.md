# Security, privacy and operations

## Boundary and controls

Local development defaults to synthetic data and loopback HTTP/PostgreSQL; credentials are generated into ignored mode0600 files. The deployment preparation adds staging/production configuration with external PostgreSQL, HTTPS origin and authenticated SMTP required at startup. No live infrastructure is provisioned. No raw documents, bank data, biometrics, external verification provider or payment processing. Private API responses use no-store; CSP, frame denial, no-referrer and content-type protection are set. Static application content contains no user data. Staging/production use Secure __Host cookies and HSTS; their API semantics are tested locally, while actual HTTPS/proxy behavior requires a target-environment test.

Session secrets and purpose-bound confirmation/reset tokens are random256-bit values stored as SHA-256 digests; passwords use Node scrypt with independent salt. Tokens expire after30 minutes and are atomically single-use. Sessions expire after7 days, rotate on login and revoke on reset, logout, deletion or suspension. A suspended user can recover a forgotten password and authenticate into restricted rights/appeal access without lifting suspension. All ordinary routes check suspension, role/ownership and confirmed-email state server-side. State-changing requests require exact Origin and JSON. IP-based limits cover general API and authentication; proxy trust defaults off and accepts only explicit verified IPs/CIDRs. On Render this can group rate limits by load-balancer socket IP until ingress is verified; a public beta must resolve this. JSON bodies and field lengths are bounded; SQL is parameterised; messages render as text.

SMTP465 uses implicit TLS; SMTP587 requires STARTTLS, with certificate verification and TLS1.2 minimum. Connections/authentication have bounded deadlines and no fallback to local files. Tokens remain in URL fragments and messages have no application tracking. Provider-side tracking, quota, bounce suppression and retention need account configuration. Registration rolls back when the provider rejects delivery; password recovery retains a generic HTTP response on delivery failure. SMTP runs synchronously during token issuance: this is not a durable mail queue or proof of timing indistinguishability. Provider acceptance does not guarantee inbox delivery.

Ordered user-row locks serialize invitations, messages, blocking, suspension, profile/property edits and deletion. Accept checks exact current revisions; offered facts are preserved separately for accepted/closed conversations. The global migration advisory lock/checksum ledger refuses changed or missing applied files. External database startup performs only schema checks, with migration an explicit operator action.

## Data and retention

Discovery returns only opaque identifiers and approved compatibility fields. Matching never reads verification, identity, language, income or protected traits; indirect effects of budget/geography/capacity remain a release research question. Fixed per-property hash ordering is not an exposure-fairness claim.

Report creation requires an actual invitation participant. Only selected message context is retained; there is no general staff chat browser. Admin/moderator actions are audited. Account deletion removes own profiles, properties, messages, tokens and own reports. Reports made by others survive independently with the selected context and nulled deleted identifiers until operator-run cleanup removes cases older than 30 days. This threshold is not a guaranteed maximum storage time. Events have no account IDs or message contents. Staff audit records retain action/reason codes with deleted IDs nulled.

Run `npm run maintenance` daily in any persisted demonstration: expired sessions/tokens, reports older than30 days, events older than30 days and audits older than90 days are removed. A daily Render cron template is prepared but has not been provisioned; local scheduling remains an operator responsibility. Local mailbox files contain synthetic email/token data; the maintenance command removes recognised files older than30 minutes. Production retention, lawful purpose and backup propagation need independent approval; these defaults are not a legal opinion.

## Operations and recovery

Use `npm run bootstrap` to create/configure the generated local cluster, `npm start` to run compiled UI/API, and Ctrl+C for graceful stop. Database files persist. Startup can recover stale lock files only when the stored cluster path matches and the recorded process is demonstrably dead/zombie; it refuses to remove a live or unrecognised process lock. No destructive database reset is part of setup.

Do not use an application database for tests. `npm test` rejects external `DATABASE_URL`, validates effective database/server identity and uses `soglia_test`; E2E owns `soglia_e2e`. The main application data is preserved. Keep port3000 free for E2E. Do not run competing database-owning lifecycle commands concurrently; a task that reuses an existing local server does not own its shutdown.

For external backups, use the PostgreSQL version-matched `pg_dump`/`pg_restore` tooling and a separate encrypted destination under the operator's policy. A local logical backup/restore drill passed against a separate disposable database; see validation evidence. Cloud backup infrastructure and a production recovery drill remain unconfigured. Test restore into a new disposable database before any real-user pilot. Never copy `.local/` into version control, shared reports or support tickets.

Current limits: single application process and per-process rate limits, no durable SMTP queue, manual moderation, maintenance templates unapplied, no public deployment, no full WCAG certification, no independent penetration test, no real-user fairness or performance-at-scale claim. Each is a release gate or explicit local scope boundary, not a hidden dependency of the demo. See [deployment instructions](deployment.md) for the prepared infrastructure and operational checks still required.

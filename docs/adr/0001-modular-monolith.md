# ADR 0001 — TypeScript modular monolith and PostgreSQL

Date: 2026-10-03. Status: accepted after independent review03.

## Decision

Use Node24 LTS with Fastify5 for the HTTP/API boundary, React19 + Vite for the browser app, TypeScript, and PostgreSQL accessed by parameterised `pg` queries. Use explicit SQL migrations with checksums/transactional ledger. One process serves the built UI and API; development may run Vite plus the API. Public landing copy is in the app; server HTML supplies metadata and no private profile is indexable. No distributed queue, Redis, ML or separate services needed for the local core.

Compared with the candidate Next/Drizzle/BetterAuth stack in research10, this has fewer framework-specific auth/action/cache boundaries for a small private app and permits direct integration testing with Fastify injection. Trade-off: auth/session/email-token logic is owned here and needs focused security tests; use Node's vetted scrypt/random primitives, opaque hashed tokens, server sessions, strict origin checks and rate limiting. No JWT or localStorage credential. Re-evaluate managed auth before production.

Use a pinned `embedded-postgres` package for Linux non-root Docker-free development (native PostgreSQL binaries distributed through npm integrity-checked packages). PostgreSQL is still a real server. Support externally supplied `DATABASE_URL`; no automatic wipe or automatic seed on an external DB. Embedded DB binds loopback and uses a random local password. An explicit setup command creates local ignored configuration. Docker is optional, not required. Lockfile is the reproducibility contract; package latest metadata is not an installation result.

## Modules and data

`server/auth` owns hashes, sessions, verification/reset tokens; `server/domain` owns compatibility and allowed transitions; `server/app` validates/authenticates API operations; database is the source of truth. `src/` owns views and presentation, receives only audience-specific DTOs. Brand/copy config is central. Route guards are convenience only; all authorisation is server-side.

Tables: users (public role tenant/landlord/both; staff role separately), sessions, auth_tokens, profiles, properties, invitations, messages, blocks, reports, verification_checks, audit_log, events, schema_migrations. Entity IDs are opaque UUIDs; aggregate events, audit and migration metadata use their declared keys. Unique user/profile and property/tenant invitation constraints; foreign keys and constrained statuses. Financial/protected traits absent. Dates/budget/occupancy validated server-side. Money integer euros; dates ISO calendar days; explicit UTC timestamps. Invitations expire after14 days, revalidate property/profile at send/accept. Transactions/row locks serialize accept/withdraw/block/pause races. Published profile/property revisions are used to detect changes.

Compatibility is conjunction of city equality (normalised supported city enum), rent<=declared max budget, property available by requested start, requested duration within property min/max and occupants<=capacity. Reasons are individual comparisons; incompatible candidates aren't labelled bad tenants. No name, age, origin, language, verification or income data enters the function. Missing required criteria prevents publication; optional fields do not affect matching. Capacity and budget may still be indirect barriers; release requires context-specific assessment.

## Security and lifecycle

Password hashes scrypt with independent salt and bounded parameters; password length12–128. Random256-bit session/token secrets stored only as SHA-256 digests, TTL/revocation, HttpOnly SameSite cookie, Secure in production. Reject cross-origin state-changing requests, constrain JSON body and route limits, parameterised SQL, plain text messages. Registration cannot set staff role or verify identity. No client-supplied user IDs for ownership. Staff actions require role and audit; no secrets/content in analytics.

Local mailbox stores verification/reset messages in an ignored local directory with restrictive permissions; no unauthenticated mailbox HTTP endpoint. Production startup refuses the local mail adapter. External SMTP is a replaceable adapter and a release requirement. External identity/income providers are unavailable; verification model exists with constrained scope/provenance/expiry/dispute, but no public fake success endpoint.

Deletion transaction removes owned search/property/message records, sessions/tokens and contact details, anonymises user linkage in minimal security audit where justified; no raw PII/message content in analytics. Reports retain minimal selected case context independently of a counterparty deletion until operator-run maintenance removes cases older than 30 days; no automatic deletion or maximum storage time is guaranteed locally. Release retention must be legally reviewed. The local maintenance command prunes expired sessions/tokens and old events; backups and production recovery are documented separately.

## Checks required

Frozen install, clean typecheck/build, migration twice (no duplicate seed), real DB integration tests including cross-user/staff permissions and concurrent transitions, unit matching boundaries/invariance, browser core loop/reset/control flows, axe and screenshots, security/dependency review, measured local performance. No local result certifies internet deployment readiness.

## Review resolutions and exact local contracts

- Dates mean requested move-in day and earliest property availability; monthly rent/budget are **total recurring monthly cost including mandatory charges**. UI labels must say so. Duration is whole months, occupancy total people, not household type.
- Pending invitations capture property and profile revision numbers. Acceptance must present and match both current revisions; any edit cancels pending invitations (including compatible rent changes) so an old offer cannot be accepted. One invitation row per property/tenant is kept permanently until related deletion; terminal decline/expiry/withdraw/cancel/closed cannot be resent in this version. UI explains this limit. Both profile pause and property pause cancel pending invites; accepted conversations persist until closed/block. Republish never silently revives an invitation.
- Mutations involving a user pair acquire ordered user-row locks; property/profile updates and invitation send/accept use the same parent-row protocol. Contact/domain mutations check suspension under lock; credential-checked restricted account rights/appeal routes allow suspended users. Block cancels pending invitations and closes accepted conversations in both directions. Close/withdraw/accept and message writes use row locks and recheck current state; no message after committed block/close.
- Local discovery ordering is a **fixed per-property hash of opaque profile IDs**, not rotation. Bounded pagination must use this same stable order. Exposure fairness is unvalidated. No optional badge appears in discovery. Tenant can inspect/correct all criteria; manual assistance and actual fairness assessment remain launch requirements.
- Auth tokens are purpose-bound, single-use and atomically consumed. Reset revokes all sessions and outstanding reset tokens. Local confirmation demonstrates a generated token only; a future real delivery can prove address control, never legal identity. Suspended accounts fail ordinary private requests. Credential-checked login provides restricted export/delete/appeal access after old sessions are revoked. Origin must exactly match configured app origin on every mutation; absent/null origins fail. Production HTTPS cookies, private response no-store, no CORS wildcard, CSP/frame protections and request limits are required; local API binds127.0.0.1 by default.
- Reports require a participant relationship to the target invitation/message. Staff receive reporter ID, stated reason, property/invitation identifiers and **only the selected message**, not a conversation dump. Submission copy discloses this. Staff identity/action/reason/time is audited; moderator can resolve cases, only admin can suspend/restore. Suspension decisions require reason and a documented external appeal route before launch.
- Export contains own account/preferences/properties, invitation metadata, own sent messages, own blocks/reports/appeals and own verification records; excludes other users' email, private profile, session/token hashes and staff-only notes. Deletion removes own messages, reports and verification data and cascading owned properties/invitations; others are told a conversation may disappear. Audit retains action/role/time/reason code, not free-text personal details, with deleted actor/subject IDs nulled. No promise to revoke copies already obtained.
- Freshness: published properties expire from discovery/invitation eligibility after30 days without owner reconfirmation; deliberate publish/reconfirm sets the timestamp. Listing/property self-attestation is not title or availability verification. Before live pilot, add and validate explicit search episodes/relist deduplication and immutable cohort reporting. Local counts remain demo counts, never opportunity KPIs.
- The local email mailbox has no HTTP route. Initial seed credentials are generated to ignored mode0600 local files; no known admin password, no production seed. External databases require explicit migration command and never receive demo seed automatically. Build scripts do not connect to a database.
- Email confirmation is required before publication, discovery, invitations or messages; saving private drafts and account controls remain available. Real address control does not verify legal identity. The synthetic seed has explicitly marked local email confirmations.
- Migration runner acquires a global advisory lock, verifies stored checksums, applies each migration transactionally, and fails on changed applied files. A separate named `_test` database is mandatory for destructive tests; `DATABASE_URL` is never reset. A second bootstrap must preserve existing state. Expiry is enforced in query/action predicates, not only by a maintenance job.

## Implementation review amendments

Unchanged property reconfirmation refreshes availability without changing its revision or cancelling pending invitations. Pauses and factual edits still cancel pending invitations. Accepted/closed invitations retain the original offered property snapshot and explicitly show when current facts changed. Report context survives deletion of an accused participant with nulled deleted identifiers, restricted to selected content and operator-run cleanup for records older than 30 days. No automatic cleanup or hard maximum storage time is promised locally. Local email confirmation is explicitly a generated-token demonstration, not proof of control of a real mailbox. These corrections supersede contrary details in the original proposal above.

## Income extension — 2026-10-03

Migration 004 extends verification lifecycle states and creates `income_attestations` (immutable, synthetic-only observation) and `income_shares` (exact check/invitation/subject/recipient, versioned consent and revocation). No financial upload or provider webhook route is enabled. `server/income.ts` defines provider/result interfaces and an unavailable real adapter; local fixture values are generated server-side from strict scenario/category enums. Changing an observation requires a new check, not an UPDATE; replacing it revokes grants and never transfers consent.

Recipient reads reuse ordered participant locks and invitation access guards, check current expiry/contact/block/suspension status and project only the summary. Share requests bind the exact preview `attestation_id`; a stale preview returns 409, including concurrent renew/share. Holder controls/export retain own rights and do not reveal financial summaries of others. No discovery field/order or compatibility input changes. New telemetry stores event names only, without amounts, content or subject identifiers.

The real integration contract must map authenticated provider outcomes, source/category/method, period, issuer and expiry; distinguish consent interruption, technical failure and insufficient evidence; and handle idempotent callbacks, late outcomes, retention and disputes. It cannot be enabled merely with credentials: a reviewed adapter and non-synthetic schema/method extension are required. [Product and release dependencies](../product/04-income-attestation.md) remain open.
